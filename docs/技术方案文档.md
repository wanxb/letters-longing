# 《尺素 Letters & Longing》技术方案文档

版本：V1.0  
状态：生产实施版  
技术方向：Next.js 静态内容站

---

## 1. 技术目标

《尺素》采用静态内容站架构。系统只负责展示、检索和构建，不提供用户写入、后台管理、在线导入或服务端业务 API。

技术目标：

1. 使用 Next.js 生成静态页面；
2. 使用 TypeScript 管理数据类型和组件接口；
3. 使用 Tailwind CSS 建立一致的视觉系统；
4. 使用 JSON / MDX 作为站点数据源；
5. 使用 Fuse.js 实现浏览器端本地搜索；
6. 使用构建脚本完成数据校验、搜索索引和 sitemap 生成；
7. 使用 GitHub + Cloudflare Pages 部署；
8. 保持低运维、低成本、可审计、可扩展。

---

## 2. 技术栈

推荐技术栈：

```text
Next.js App Router
React
TypeScript
Tailwind CSS
MDX
Fuse.js
Cloudflare Pages
```

选择 Next.js 的原因：

1. 当前 Demo 基于 React，迁移成本低；
2. 适合实现搜索、筛选、复制、卡片列表等交互；
3. 静态生成能力满足内容站需求；
4. App Router 便于组织页面、元信息和布局；
5. 后续如需小规模动态能力，迁移路径更平滑。

暂不选择 Astro 的原因：

1. 当前 React Demo 需要额外改造；
2. 第一版交互筛选和组件迁移优先级更高；
3. 团队当前更需要快速上线，而不是重新建立 Astro 工程习惯。

---

## 3. 架构概览

```text
Codex 内容研究与整理
        ↓
JSON / MDX 数据文件
        ↓
数据校验脚本
        ↓

        ↓

        ↓
```

系统不包含：

- 数据库；
- 后台管理；
- 用户登录；
- 用户上传；
- Excel / CSV 导入界面；
- 服务器业务 API；
- AI 在线生成能力。

## 4. 存储方案

当前阶段不引入数据库，使用文件存储即可满足产品需求。

采用文件存储的原因：

1. 内容是编辑型、低频更新，不是用户实时写入数据；
2. 项目不做登录、上传、投稿、收藏、评论或后台管理；
3. MVP 和 V1 数据规模可控，JSON / MDX 足以支撑静态构建和本地搜索；
4. 文件存储可通过 Git 追踪版本，便于审查、回滚和协作；
5. 静态页面更利于 SEO、部署简单、访问稳定；
6. 不需要数据库备份、迁移、权限、连接池或服务端 API，运维成本最低。

当前存储结构：

```text
data/
  letters.json
  excerpts.json
  tags.json
  topics.json
  sources.json

content/
  letters/*.mdx
  topics/*.mdx

public/
  search-index.json
```

数据库触发条件：

1. 开放用户投稿、收藏、评论或个人内容；
2. 需要后台在线编辑和多人审核工作流；
3. 内容每天大量新增，且必须在线发布；
4. 数据量达到数万到数十万条，静态构建或本地搜索明显吃力；
5. 需要复杂查询、权限控制或实时个性化推荐。

在这些条件出现前，数据库属于过早复杂化，不进入当前技术方案。

## 6. 数据源设计

数据由 Codex 研究、整理后直接提交为 JSON / MDX。

JSON 用于结构化列表与筛选：

- `letters.json`：信件元数据；
- `excerpts.json`：短句数据；
- `tags.json`：标签体系；
- `topics.json`：专题元数据；
- `sources.json`：来源和版权信息。

MDX 用于长内容：

- 信件正文；
- 专题正文；
- 作者或来源说明；
- 需要排版的编辑内容。

## 8. 数据校验规则

构建前必须校验：

1. 所有 `id` 唯一；
2. 所有 `slug` 唯一；
3. `letterId` 引用存在；
4. `sourceId` 引用存在；
5. 发布内容不得使用 `Unknown`；
6. 所有公开信和摘录必须有来源说明；
7. `SiteCuration` 只可用于本站整理、翻译、白话解释等二次说明内容，不可标记为历史原文；
8. `qualityScore` 范围为 `0 - 100`；
9. 发布短句必须有 `plainExplanation`、`usageScene` 和至少一个标签；
10. 发布信件必须有标题、作者、摘要和来源；
11. `publishStatus = draft` 的内容不进入页面、搜索索引或 sitemap。

校验失败时构建应失败，避免错误内容上线。

## 9. 搜索方案

搜索采用 Fuse.js 本地索引。

构建产物：

```text
public/search-index.json
```

索引对象包含：

1. 短句原文、译文、现代改写、解释、标签；
2. 信件标题、作者、收信人、摘要、标签；
3. 专题标题、描述、标签；
4. URL、类型、语言、关系、情绪。

搜索体验：

1. 首页提供全站搜索入口；
2. 开头馆和结尾馆提供站内筛选搜索；
3. 搜索结果按短句、信件、专题分组；
4. 支持空状态推荐关键词；
5. 输入应做 debounce，避免每个字符触发过重计算。

适用规模：

```text
MVP：200 条短句，50 封信，5 个专题
V1：1000 条短句，300 封信，10 个专题
```

该规模适合浏览器本地搜索。超过 5 万条数据后再评估 Meilisearch 或其他搜索服务。

## 10. SEO 方案

必须实现：

1. 每个详情页独立 `title` 和 `description`；
2. 首页、列表页、详情页、专题页生成 canonical URL；
3. 自动生成 sitemap；
4. 自动生成 robots.txt；
5. 书信详情页和短句详情页输出结构化数据；
6. Open Graph 和 Twitter Card 基础信息；
7. 草稿内容不进入 sitemap；
8. 404 页面提供回到搜索和主要分类的入口。

标题策略：

```text
短句详情：{短句前半句} - 书信{类型} | 尺素
信件详情：{标题} - {作者}写给{收信人} | 尺素
专题详情：{专题标题} | 尺素
```

## 11. UI 技术规范

视觉系统应基于 Tailwind tokens，不在组件中散落任意颜色和尺寸。

建议建立：

1. 色彩 token：背景、文本、边框、主色、强调色、状态色；
2. 字体 token：标题、正文、引文、标签、按钮；
3. 间距 token：4 / 8 / 12 / 16 / 24 / 32 / 48 / 64；
4. 圆角 token：卡片不超过 8px，按钮和输入保持克制；
5. 阴影 token：只用于浮层、下拉、轻量卡片；
6. focus ring token：所有交互控件统一。

响应式要求：

1. 移动端优先；
2. 最小支持宽度 360px；
3. 正文阅读容器桌面端建议不超过 720px；
4. 列表和筛选在移动端避免横向滚动；
5. 固定顶部或底部元素不得遮挡内容；
6. 图片和媒体必须预留尺寸，避免 CLS。

交互要求：

1. 复制、筛选、搜索都要有即时反馈；
2. 列表项 hover 不改变布局尺寸；
3. 所有图标按钮必须带 `aria-label`；
4. 所有可点击卡片必须明确主操作；
5. 动效只使用 opacity / transform；
6. 支持 `prefers-reduced-motion`。

```json
{
  "scripts": {

    "validate:data": "tsx scripts/validate-data.ts",
    "build:search": "tsx scripts/build-search-index.ts",
    "build:sitemap": "tsx scripts/build-sitemap.ts",
    "check:links": "tsx scripts/check-source-links.ts",
    "build": "npm run validate:data && npm run build:search && npm run build:sitemap && next build",
    "lint": "next lint",
    "typecheck": "tsc --noEmit"
  }
}
```

## 13. 部署方案

推荐：

```text
GitHub + Cloudflare Pages
```

部署流程：

```text
提交代码和数据
  ↓
Cloudflare Pages 触发构建
  ↓
数据校验
  ↓
生成搜索索引与 sitemap
  ↓
Next.js 静态构建
  ↓
发布静态站点
```

生产构建失败条件：

1. 数据校验失败；
2. 类型检查失败；
3. lint 失败；
4. sitemap 或搜索索引生成失败；
5. 静态页面构建失败。
